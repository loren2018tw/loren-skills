# 技能內腳本的非 Linux 平台相容性

Status: ready-for-agent
Category: enhancement

## 背景

技能內由 agent 執行的腳本目前假設 Unix 環境：

- `doc-to-markdown-with-image/scripts/doc-to-md.sh`：`#!/usr/bin/env bash`，依賴 bash 環境與 GNU 工具（`readlink -f --`、`mktemp -d`）；macOS 內建 `readlink` 不支援 `-f`。
- 兩支 `SKILL.md` 寫死 `bash scripts/…` 與 `python3 scripts/…`；Windows 上的 Python 指令通常是 `py -3` 或 `python`。
- `merge_md_images.py`、`convert_to_blooket.py` 為純標準庫 Python，本身大致跨平台，但 Windows 的 stdout 編碼（CP950 主控台／pipe）可能使中文輸出失敗或亂碼。

## 待決

- 支援目標平台是哪幾個（Windows？macOS？）
- 提供 PowerShell 等效腳本、改寫成 Python-only、或以文件化依賴（Git Bash／WSL＋python3）處理
- agent 在 Windows 上的執行 shell 是什麼（未經實機確認）

（本票出自 `grill-with-docs` 會談：安裝工具鏈收斂為 PowerShell 7 之後，特意留出的範圍外後續。）

## Agent Brief

**Category:** enhancement
**Summary:** 技能內腳本改為 Python 單一實作、補齊 Windows 跨平台缺口（直譯器呼叫、編碼、工具定位），並以 CI 腳本層煙霧與不變式防回歸

**Current behavior:**

- `doc-to-markdown-with-image` 的轉換腳本是 bash 實作，依賴 `readlink -f` 等 GNU 行為（macOS 不支援），Windows 需 Git Bash（預設不在 PATH）；其 SKILL.md 寫死 `bash scripts/…`。
- `gimkit-to-blooket` 的 SKILL.md 寫死 `python3 scripts/…`；Windows 的 `python3` 幾乎必是 Microsoft Store 執行別名，可靠的直譯器名稱是 `py`（python.org 安裝器預設提供）。
- 兩支 Python 腳本的 stdout 以中文／emoji 輸出；zh-TW Windows 的 CP950 pipe 下，blooket 轉換腳本會擲 `UnicodeEncodeError`（已實測；且發生在輸出檔已寫出之後）。
- LibreOffice 在 Windows／macOS 通常不在 PATH；`uv tool install markitdown` 的 shim 目錄也不一定在 PATH；soffice 的 `-env:UserInstallation=file://…` URI 在 Windows 會組出非法形式。
- 技能腳本無 CI 覆蓋；AGENTS.md 無跨平台不變式。

**Desired behavior:**

- 技能內腳本一律 Python（純標準庫）單一實作，不假設 bash／pwsh 存在（依 ADR 0004）。
- `doc-to-markdown-with-image` 的轉換腳本以 Python 重寫並取代原 bash 腳本；CLI 與輸出契約不變：`<來源文件> [輸出資料夾]`、預設輸出 `<stem>.md` + `assets/`、佔位符對位異常時 exit 2 警告、成功時印出 md 路徑；管線不變（.doc 先經 soffice 橋接 → markitdown → 合併腳本還原圖片）。
- 直譯器呼叫：Windows 用 `py -3`，macOS/Linux 用 `python3`；兩支 SKILL.md 以平台分支表呈現，附 fallback 一行（表中指令不存在時試另一種名稱；都沒有則回報安裝指引，不得臨場改寫管線）。
- 所有腳本 stdout/stderr 明確以 UTF-8 輸出，在非 UTF-8 主控台／pipe（含 CP950）下不崩潰。
- 工具定位：先查 PATH，再查少量常見安裝位置（LibreOffice 於 Windows／macOS 的標準安裝路徑；uv 的 shim 目錄），都沒有才以安裝指引失敗；markitdown 額外支援以當前直譯器 `-m markitdown` 執行（pip 安裝情境）。
- soffice 的 UserInstallation URI 以跨平台方式組出（Windows 上須為合法 `file://` URL）；合併腳本內的同款呼叫一併修正。
- CI（ubuntu-latest + windows-latest）新增腳本層煙霧測試：blooket 轉換（含 CP950 pipe）、圖片合併（動態生成最小 docx）、docx 全管線（以 pip 安裝 markitdown、pin 已知相容版本；重量級的 LibreOffice 不入 CI）；AGENTS.md 新增跨平台不變式；README 補一句技能腳本支援範圍（官方 Linux＋Windows；macOS best-effort）。

**Key interfaces:**

- 轉換腳本 CLI：`<來源文件> [輸出資料夾]`；exit 0 成功、1 環境／輸入錯誤、2 佔位符對位警告（維持現行契約）
- SKILL.md 指令呈現：平台分支表 + fallback 行（文件語言為繁中）
- 工具定位：單一查詢函式，回傳可執行路徑；失敗時錯誤訊息含可執行的安裝指引
- CI smoke：以測試中動態生成的 fixture（CSV、最小 docx）驅動，不提交二進位 fixture

**Acceptance criteria:**

- [ ] 舊 bash 轉換腳本已移除，repo 內無殘留引用（SKILL.md、README、CI）
- [ ] 兩平台 CI 上，blooket 轉換腳本對 fixture CSV 執行成功且輸出逐題正確
- [ ] 兩平台 CI 上，blooket 轉換腳本在 `PYTHONIOENCODING=cp950` 下不崩潰，exit code 與訊息契約維持
- [ ] 兩平台 CI 上，docx 全管線（不含 soffice）通過：fixture docx → markitdown → 圖片抽出、改名與 md 引用皆正確，且無 `data:image` 殘留
- [ ] 兩平台 CI 上，圖片合併腳本對動態生成的最小 docx 正確抽出圖片；soffice 缺席時 emf/wmf 警告但不崩潰
- [ ] 工具缺席時，轉換腳本以 exit 1 給出含安裝指令的訊息、無 traceback
- [ ] 兩支 SKILL.md 已改為平台分支＋fallback；doc-to-markdown 的環境需求段落同步更新
- [ ] `.github/workflows/checks.yml` 的兩個 runner 全綠，既有 checks（編碼不變式、install 生命週期）不受影響
- [ ] 實作符合 ADR 0004；AGENTS.md 含跨平台不變式一行；README 有支援範圍一句

**Out of scope:**

- macOS 的 CI 驗證與任何「已支援 macOS」的文件措辭（best-effort 平台）
- 需 LibreOffice／soffice 的 .doc 全管線 CI 覆蓋
- 安裝腳本（install.sh／install.ps1／install.cmd）與安裝流程的任何變更
- 無腳本技能（create-flashcards、create-gimkit-questions、textbook-analysis、who-is-loren）的改動
- Windows／macOS 實機人工測試（驗證以 CI 為準，比照 ADR 0003）
